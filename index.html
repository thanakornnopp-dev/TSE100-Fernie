Section 01 • Architecture & Mechanics

หลักการทำงานและสถาปัตยกรรมระบบอย่างละเอียด

วิเคราะห์เจาะลึก 5 องค์ประกอบหลักที่ทำให้ระบบทำงานได้อย่างมีเสถียรภาพและปลอดภัยระดับอุตสาหกรรม

1. Dual-Core FreeRTOS Decoupling

หัวใจหลักของการประมวลผลบน ESP32 (Xtensa 32-bit LX6 240MHz):

  • Core 1 (Hardware Engine): รันฟังก์ชัน loop() ตรวจวัดเซนเซอร์ PIR (GPIO 27) และ LDR (GPIO 34) ทุกๆ ไม่ถึง 100 µs เพื่อสั่งเปิด-หรี่ไฟทันที (< 1 ms)
  • Core 0 (Telemetry Engine): รัน telemetryTask ดูแล Wi-Fi และยิง HTTPS POST ไปยัง Cloud โดยไม่บล็อกการติดของหลอดไฟ
  • IPC Inter-Task Notify: สื่อสารระหว่าง Core ด้วย xTaskNotifyGive() เมื่อมีคนเดินผ่าน ปลุก Core 0 ขึ้นมาส่งเน็ตทันที
Thread-Safe Zero-Latency Control

3. Campus Safety Watchdog

ระบบเฝ้าระวังภัยคุกคามและการบาดเจ็บบริเวณจุดอับยิม 7:

  • Loitering Detection (>25s): หากมีคนยืนแช่ในรัศมีเซนเซอร์นานผิดปกติเกิน 25 วินาที ระบบจะส่งสัญญาณเตือน LOITERING_ALERT ทันที
  • Edge-Triggered Foot Traffic: ตรวจจับ Rising Edge สัญญาณ PIRเพื่อนับจำนวนรอบการเดินผ่านจริง ป้องกันการนับเบิ้ล (Double-Counting)
  • Hardware Diagnostic LED: ไฟสีน้ำเงินบนบอร์ด ESP32 (GPIO 2) แจ้งสถานะเชื่อมต่อ Wi-Fi สดหน้างาน

Section 03 • Comprehensive Defense Preparation

15 คำถามเจาะลึกที่อาจารย์และกรรมการจะถาม

คัดสรรคำถามจริงจากมุมมองวิศวกรรมไฟฟ้า คอมพิวเตอร์ และโครงสร้างพื้นฐาน พร้อมแนวตอบระดับ First Principles

🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

วัดความเข้าใจเรื่อง Real-Time System, ปัญหา I/O Network Blocking บนไมโครคอนโทรลเลอร์ และการจัดสรรคอร์ประมวลผล

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"เนื่องจาก ESP32 มีชิป 2 คอร์ หากเราเขียนโค้ดรวมใน loop() เดียวบนคอร์เดียว เมื่อระบบต้องยิง HTTPS POST ไปยัง Google Apps Script กระบวนการเชื่อมต่อ SSL และรับส่งข้อมูลจะทำให้ CPU บล็อก (Network Blocking) ค้างนาน 1.5 ถึง 2.0 วินาที ซึ่งในเวลานั้นหากมีคนเดินผ่าน เซนเซอร์จะไม่สามารถตอบสนองได้ และไฟทางเดินจะติดช้าไม่ทันที

เราจึงแยกหน้าที่: Core 1 รับผิดชอบเฉพาะ Hardware Control Loop ตรวจจับเซนเซอร์และสั่งเปิด-หรี่ไฟระดับ Real-Time (< 1 ms) ส่วน Core 0 ทำงานเป็น FreeRTOS Background Task คอยดูแลการส่งข้อมูลขึ้น Cloud และบริหารจัดการ Wi-Fi โดยสื่อสารกันข้ามคอร์ผ่าน FreeRTOS Direct Task Notifications (xTaskNotifyGive) ซึ่งทำให้ระบบเปิดไฟได้ทันทีโดยไม่มีการหน่วง (Zero Latency) ครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "เพราะโค้ดยาวเลยแยกคอร์" หรือ "ก๊อปโค้ดตัวอย่างมาจากอินเทอร์เน็ต"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบว่าเข้าใจความแตกต่างระหว่าง "Control Path" (การสั่งงานฮาร์ดแวร์ตรง) กับ "Telemetry Path" (การรายงานผลขึ้นระบบ) หรือไม่

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"เกิดจากการแยก Asynchronous Decoupling ครับ หลอดไฟเชื่อมต่อทางกายภาพกับขา PWM (GPIO 18) ของ ESP32 เมื่อคนเดินผ่านหน้า PIR บอร์ดบน Core 1 จะสั่งฟังก์ชัน ledcWrite() สลับดิวตี้ไซเคิลเป็น 100% โดยตรงในเวลาไม่ถึง 1 มิลลิวินาที หลอดไฟจึงสว่างวาบนำทางทันที

ส่วนความหน่วง 1-2 วินาทีนั้นเกิดขึ้นใน Core 0 ซึ่งเป็นช่องทาง Telemetry สื่อสารผ่านโปรโตคอล HTTPS ข้ามไปยังเซิร์ฟเวอร์ Google ที่อยู่ภายนอก ซึ่งเป็นเพียงการส่งสถิติและอัปเดตหน้าจอแดชบอร์ด จึงไม่มีผลกระทบต่อความปลอดภัยและประสบการณ์ของผู้ใช้งานหน้างานจริงครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "เน็ตของบอร์ดเราเร็วมากจนส่งถึง Google ได้ใน 1 ms" เพราะขัดแย้งกับหลักเครือข่ายพื้นฐาน
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

วัดความเข้าใจเรื่อง Power Management, ประสิทธิภาพวงจร (Efficiency), การป้องกันวงจรเสียหาย และหลักการ YAGNI (ไม่ใส่อุปกรณ์เกินจำเป็น)

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"เราเลือกตัด Step-Up ออกด้วยเหตุผลทางวิศวกรรม 3 ข้อครับ:
1. ความเข้ากันได้ของแรงดัน (Voltage Matching): เซนเซอร์ PIR (HC-SR501), LDR, และโมดูลหลอดไฟ LED ของเราทำงานที่ระดับแรงดัน 5V DC อยู่แล้ว ซึ่งตรงกับแรงดันจากสาย USB หรืออะแดปเตอร์ไฟ 5V Mains พอดี การเร่งเป็น 12V แล้วต้องมาทอนไฟลงจะทำให้เกิด Switching Loss สูญเสียพลังงานโดยเปล่าประโยชน์ 15-20%
2. ความปลอดภัยของชิป (Component Protection): ขา GPIO ของ ESP32 รับแรงดันได้สูงสุด 3.3V หากใช้วงจร Step-Up 12V ที่ไม่มีวงจรแยกทางไฟฟ้า (Optoisolator) มีความเสี่ยงสูงที่แรงดันเกินจะกระชากเข้าทำลายชิปและทำให้หลอด LED ขาดในทันที
3. ความเสถียรของระบบ (LDO Stability): บอร์ด ESP32 มี Onboard LDO Regulator แปลง 5V จากช่อง VIN เป็น 3.3V จ่ายชิปประมวลผลได้อย่างราบเรียบ การใช้ระบบ Single 5V Rail จึงเสถียร ประหยัดต้นทุน และปลอดภัยที่สุดครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "ลืมซื้อ Step-Up" หรือ "ไม่มีเงินซื้อ"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบความเข้าใจเชิงลึกเกี่ยวกับรังสีคลื่นความร้อนอินฟราเรด (Infrared Radiation) และโครงสร้างเลนส์ Fresnel

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"เซนเซอร์ PIR (Passive Infrared) ตรวจจับการเปลี่ยนแปลงของรังสีอินฟราเรดย่านความร้อนคลื่นยาว (~9.4 µm) ที่แผ่ออกมาจากร่างกายมนุษย์ (อุณหภูมิประมาณ 36-37°C) ภายในมีผลึก Pyroelectric สองขั้วต่อกลับเฟสกัน และมีฝาครอบเลนส์ Fresnel ที่ซอยโซนตรวจจับเป็นช่องๆ

เมื่อคนเดินตัดผ่าน รังสีความร้อนจะตกกระทบผลึกช่องที่ 1 และช่องที่ 2 สลับกัน เกิดเป็นผลต่างแรงดันรูปคลื่น Sine Wave วงจรจึงสั่ง Trigger เอาต์พุตเป็น HIGH แต่หากเป็นลมพัดหรือกิ่งไม้ไหวที่อุณหภูมิเท่ากับสภาพแวดล้อม รังสีความร้อนทั้งสองช่องจะตกกระทบเท่ากันและหักล้างกันเป็นศูนย์ จึงไม่เกิด False Trigger ครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "PIR ยิงลำแสงอินฟราเรดออกไปแล้วสะท้อนกลับมา" เพราะนั่นคือเซนเซอร์ Active IR ไม่ใช่ Passive IR
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ตรวจสอบความรู้เรื่องข้อจำกัดของวงจรแปลงสัญญาณ Analog-to-Digital (ADC) บนบอร์ด ESP32 และการปรับจูนระบบหน้างาน

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"ด้วยเหตุผล 2 ประการครับ:
1. ข้อจำกัด ADC ของ ESP32: ชิป ESP32 มีพฤติกรรม Non-linearity ของ ADC ค่อนข้างสูง โดยเฉพาะช่วงแรงดันต่ำกว่า 0.1V และสูงกว่า 3.2V ทำให้การอ่านค่าความเข้มแสงแอนะล็อกมีความคลาดเคลื่อนและต้องใช้เวลาสอบเทียบ (Calibration)
2. ลดภาระ CPU และจูนง่ายหน้างาน: ระบบของเราต้องการเพียงคำตอบสองสถานะคือ 'มืดแล้วหรือยัง' โมดูล LDR ที่มาพร้อมชิปเปรียบเทียบแรงดัน LM393 มีตัวต้านทานปรับค่าได้ (Trimpot) ทำให้ช่างเทคนิคปรับเกณฑ์แสงสว่างหน้างานได้ด้วยไขควงทันที สัญญาณ DO ที่ส่งมาเป็นระดับลอจิกดิจิทัลตัดปัญหาเรื่องสัญญาณรบกวน (Noise Immunity) และไม่กินรอบเวลาของ CPU ในการสุ่มตัวอย่าง ADC ครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "เขียนโค้ดอ่าน Analog ไม่เป็น"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบความเข้าใจเรื่องข้อจำกัดเชิงกายภาพของเซนเซอร์ PIR และตรรกะ Edge-Triggering ในโค้ด

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"ในโค้ดเราใช้ตรรกะ Rising-Edge Detection (prevPirState == LOW && pirState == HIGH) ซึ่งจะนับจำนวนก้าวเพิ่มขึ้นเพียง 1 ครั้งในเสี้ยววินาทีแรกที่คนเดินเข้ามาในรัศมีตรวจจับ แม้คนผู้นั้นจะหยุดยืนนิ่งหรือเดินต่อจนสัญญาณ PIR ค้างเป็น HIGH ตัวนับจะไม่เพิ่มขึ้นซ้ำซ้อนครับ

อย่างไรก็ตาม ในกรณีที่คนเดินเคียงคู่กันเป็นกลุ่ม เซนเซอร์ PIR เดี่ยวจะมองเห็นเป็น 1 เหตุการณ์เดินผ่าน (Passage Event) ซึ่งเป็นข้อจำกัดทางกายภาพของเซนเซอร์อินฟราเรด หากในอนาคตต้องการนับแยกรายคนแบบแม่นยำ 100% สามารถเสริมเซนเซอร์ Time-of-Flight (ToF) แบบคู่เพื่อทำม่านตรวจจับ หรือใช้กล้อง Edge-AI ขนาดเล็กประมวลผลแทนได้ครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามอ้างว่า "PIR ตัวนี้นับคนในกลุ่มได้เป๊ะ 100%" เพราะเป็นไปไม่ได้ในหลักวิศวกรรมของเซนเซอร์ตัวเดียว
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบว่าฟีเจอร์นี้ถูกออกแบบขึ้นมาตอบโจทย์ปัญหาจริง (Problem-Solving Value) หรือเป็นเพียงฟังก์ชันสร้างขึ้นมาลอยๆ

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"ทางเดินริมยิม 7 มีลักษณะเป็นทางสัญจรยาวและค่อนข้างเปลี่ยวในยามค่ำคืน จากการศึกษาพฤติกรรมคนเดินเท้าทั่วไปจะใช้เวลาสัญจรผ่านรัศมีตรวจจับ 6 เมตรประมาณ 4-8 วินาทีเท่านั้น หากเซนเซอร์ PIR มีสัญญาณค้างต่อเนื่องยาวนานเกิน 25 วินาที แสดงถึงสภาวะผิดปกติ เช่น มีนักศึกษาเป็นลมหมดสติ, เกิดการทะเลาะวิวาท, หรือมีบุคคลน่าสงสัยมาดักซุ่มรอ

เมื่อตัวจับเวลาใน Core 1 ครบ 25 วินาที ระบบจะเปลี่ยนสถานะเป็น LOITERING_ALERT เร่งไฟส่องสว่าง 100% เพื่อป้องปรามเหตุ และสั่งปลุก Core 0 ยิงแจ้งเตือนไปยังคลาวด์และ LINE รปภ. มหาวิทยาลัยทันทีเพื่อส่งเจ้าหน้าที่มาตรวจสอบจุดเกิดเหตุครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "ตั้งเวลา 25 วินาทีมั่วๆ ไม่มีที่มา"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

วัดความเข้าใจเรื่อง Power Electronics, ปรากฏการณ์ Flicker Effect ในกล้อง และคลื่นเสียงรบกวน (Audible Noise)

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"การเลือกความถี่ 5,000 Hz มีเหตุผลทางวิศวกรรม 3 ประการครับ:
1. ขจัดแถบดำในกล้อง (Zero Camera Flicker): ความถี่ต่ำกว่า 1 kHz แม้ตาเปล่าจะมองไม่เห็นการกะพริบ แต่เมื่อนักศึกษาใช้กล้องสมาร์ทโฟนถ่ายรูปหรือวิดีโอตอนกลางคืน จะเกิดคลื่นแถบดำวิ่งผ่านภาพ (Rolling Shutter Artifacts) ซึ่งที่ความถี่ 5 kHz จะเนียนตาและไร้แถบดำ 100%
2. ลดเสียงหวีดในวงจร (Acoustic Noise Mitigation): ความถี่ 500 Hz ถึง 2 kHz มักทำให้ขดลวดหรือตัวเก็บประจุเซรามิกเกิดการสั่นสะเทือนแบบ Piezoelectric รบกวนคนเดินด้วยเสียงหวีดแหลม การขยับขึ้นมาที่ 5 kHz ช่วยลดคลื่นเสียงกวนใจได้มาก
3. สมดุลกับ Switching Loss: ความถี่ 5 kHz ไม่สูงเกินไปจนทำให้ทรานซิสเตอร์ MOSFET เกิดความร้อนสะสมจากการสลับสัญญาณ (Switching Loss) และไม่รบกวนความถี่วิทยุ 2.4GHz ของ Wi-Fi ครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "ใส่เลข 5000 ตามใจชอบ ไม่มีเหตุผล"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบหลักการออกแบบระบบวิกฤต (Safety-Critical Fail-Safe) ว่าขึ้นอยู่กับอินเทอร์เน็ตจนทำให้ไฟดับหรือไม่

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"ระบบเปิด-ปิดไฟยังทำงานได้ตามปกติสมบูรณ์แบบ 100% ครับ! เพราะตรรกะการควบคุมไฟทั้งหมดทำงานอยู่ใน Core 1 แบบ Local Edge Computing โดยไม่พึ่งพาอินเทอร์เน็ตเลยแม้แต่น้อย

เมื่อเน็ตหลุด Core 0 จะดับไฟ LED สถานะ (GPIO 2) ลงเพื่อแจ้งเตือนช่างหน้างาน และสั่งเรียกใช้ฟังก์ชัน WiFi.reconnect() แบบไม่บล็อกการทำงาน (Non-blocking retry) เมื่อสัญญาณ Wi-Fi กลับมา ระบบจะต่อเชื่อมและกลับมารายงานสถิติขึ้น Google Sheets ต่อทันทีโดยอัตโนมัติครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "ถ้าเน็ตหลุดไฟจะดับทั้งยิม" เพราะระบบโครงสร้างพื้นฐานเพื่อความปลอดภัยห้ามล่มเด็ดขาด
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

วัดความเข้าใจเรื่องสถาปัตยกรรมคลาวด์ของ Google และข้อจำกัดด้านหน่วยความจำของไมโครคอนโทรลเลอร์ในการทำ SSL Handshake

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"มีเหตุผลทางสถาปัตยกรรมเว็บสองเรื่องครับ:
1. ทำไมต้อง 302 Redirect: สถาปัตยกรรมของ Google Apps Script เมื่อได้รับ HTTP POST เข้ามาที่ URL ปลายทาง ระบบจะทำการ Redirect ผู้ส่งไปยังเซิร์ฟเวอร์ย่อยที่ให้บริการเอกสารด้วยรหัส HTTP 302 Moved Temporarily ในโค้ด ESP32 จึงต้องรับรู้ว่ารหัส 302 หรือ 200 หมายถึงข้อมูลบันทึกลง Google Sheet สำเร็จแล้ว
2. ทำไมต้อง setInsecure(): เนื่องจาก Google มีการหมุนเวียนใบรับรอง SSL Root Certificate เป็นประจำ หากเราฝัง Certificate Fingerprint แบบตายตัวในบอร์ด เมื่อ Google ปรับเปลี่ยนใบรับรอง บอร์ดจะไม่สามารถส่งข้อมูลได้ทันที อีกทั้งการตรวจสอบ Handshake เต็มรูปแบบกิน RAM และเวลาคำนวณของ ESP32 มากเกินไป การข้ามการตรวจสอบในข้อมูล Telemetry ทั่วไปจึงช่วยให้ระบบคล่องตัวและทนทานที่สุดครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "ไม่รู้ว่า 302 คืออะไร ใส่ตามโค้ดตัวอย่าง"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

วัดความเข้าใจเรื่อง Concurrency, Thread Safety, Critical Section และกลไก IPC ของ FreeRTOS

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"ในสถาปัตยกรรมแบบมัลติคอร์ ย่อมมีความเสี่ยงเรื่อง Race Condition หากสองคอร์พยายามเขียนตัวแปรพร้อมกัน แต่ในระบบของเราได้ป้องกันด้วย 2 มาตรการครับ:
1. หลักการ Single-Writer Multiple-Reader Pattern: ตัวแปรสถิติทั้งหมด (trafficCount, motionActive, currentDutyCycle) ถูกเขียนและแก้ไขโดย Core 1 เพียงคอร์เดียวเท่านั้น ส่วน Core 0 ทำหน้าที่เป็นผู้บริโภค (Reader) ที่ดึง Snapshot ล่าสุดไปสร้าง JSON Payload จึงไม่เกิดการเขียนทับกันแย่งชิงข้อมูล
2. กลไกการส่งสัญญาณ Atomic: เราใช้ฟังก์ชัน xTaskNotifyGive() และ ulTaskNotifyTake() ซึ่งเป็นคำสั่งระดับเคอร์เนลของ FreeRTOS ที่เป็น Thread-Safe 100% ทำให้ไม่จำเป็นต้องใช้ Mutex Lock ที่กิน Overhead สูงครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "ไม่มีทางชนกันอยู่แล้วเพราะ ESP32 จัดการให้เองอัตโนมัติ" (ESP32 ไม่ได้จัดการแชร์ตัวแปรข้ามคอร์ให้อัตโนมัติหากไม่เขียนโค้ดคุม)
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบความสามารถในการให้ตัวเลขเชิงปริมาณ (Quantified Engineering Evidence) และการวิเคราะห์ผลตอบแทนความคุ้มค่า

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"เราสามารถคำนวณเปรียบเทียบในรอบกลางคืน 12 ชั่วโมง (18:00 - 06:00 น.) ได้อย่างชัดเจนครับ:
• เสาไฟถนนเดิม: เปิด 100% ตลอดทั้ง 12 ชั่วโมง กินไฟ 8.5W ตลอดเวลา คิดเป็นพลังงาน = 8.5W × 12h = 102.0 Wh ต่อคืน
• เสาไฟอัจฉริยะ TSE100: จากข้อมูล Foot-traffic เฉลี่ย มีคนเดินผ่านรวม 3 ชั่วโมง (กินไฟ 8.5W × 3h = 25.5 Wh) และช่วงปลอดคน 9 ชั่วโมงอยู่ในโหมดหรี่ Eco 30% (กินไฟ 2.8W × 9h = 25.2 Wh) รวมพลังงานต่อคืน = 50.7 Wh

จะเห็นว่าระบบของเราลดการใช้พลังงานลงได้ถึง 50.3% ในวันปกติ และหากเป็นช่วงปิดเทอมหรือช่วงดึกสงัดที่มีคนสัญจรน้อย อัตราการประหยัดไฟจะสูงเกิน 70% ครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "ประหยัดได้เยอะครับ แต่ไม่ได้คำนวณตัวเลขมา"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบการออกแบบเพื่อการใช้งานจริง (Design for Serviceability & Diagnostics) โดยไม่ต้องต่อคอมพิวเตอร์ดู Serial Monitor

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"ไฟ LED สีน้ำเงินบนบอร์ด ESP32 (GPIO 2) ทำหน้าที่เป็น Hardware Network Health Indicator เพื่อให้ช่างเทคนิคตรวจเช็กระบบได้ด้วยตาเปล่า:
• ไฟดับสนิท (OFF): ระบบออฟไลน์ Wi-Fi ขาดการเชื่อมต่อ และกำลังอยู่ในโหมดพยายามเชื่อมต่อใหม่
• ไฟติดสว่างค้าง (Solid ON): เชื่อมต่อโครงข่ายไร้สายสำเร็จ และกำลังส่งสถิติ Telemetry ขึ้นคลาวด์ได้อย่างราบรื่น
สิ่งนี้ช่วยลดเวลาในการตรวจแก้ปัญหา (Troubleshooting) หน้างานอย่างมาก เพราะไม่ต้องปีนบันไดนำโน้ตบุ๊กไปเสียบสาย Serial Monitor ดูโค้ดครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "เปิดไฟไว้ให้ดูสวยงามเฉยๆ"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบความพร้อมในการใช้งานจริง (Field Readiness) การจัดการความร้อน ความชื้น และมาตรฐานทางวิศวกรรมโยธาและไฟฟ้า

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"มีสิ่งท้าทายจากธรรมชาติ 3 ประการที่ต้องออกแบบป้องกันตามมาตรฐานครับ:
1. ฝนและความชื้น: วงจรทั้งหมดต้องบรรจุในกล่องกันน้ำมาตรฐาน IP65 มีขอบยางซิลิโคนและข้อต่อ Cable Gland ป้องกันน้ำซึมเข้าจุดต่อสายไฟ
2. ความร้อนสะสมและแสง UV: เลนส์ Fresnel ของ PIR ทำจากโพลีเอทิลีนซึ่งไวต่อแสงแดดและอาจกรอบแตก จึงต้องออกแบบหมวกบังแดด (Sun Hood) ปกป้องตัวเซนเซอร์ และบอร์ด ESP32 ควรติดแผ่นระบายความร้อน (Heatsink) ในตัวเคส
3. แมลงและละอองน้ำ: แมลงที่บินมาเกาะหน้าเซนเซอร์อาจทำให้เกิด False Trigger จึงต้องปรับค่าความไว (Sensitivity Potentiometer) ให้พอเหมาะกับระยะทางเดิน 5-6 เมตร และใช้ฟังก์ชันกรองสัญญาณกวนในซอฟต์แวร์ครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "เอาเบรดบอร์ดและสายไฟเปลือยไปแขวนบนต้นไม้หรือเสาไฟได้เลย"
🎯 เจตนาของอาจารย์ / สิ่งที่กรรมการต้องการทดสอบ:

ทดสอบวิสัยทัศน์สถาปัตยกรรมระบบขนาดใหญ่ (Enterprise IoT Architecture) และความรู้เรื่องโปรโตคอล MQTT / Time-Series Database

💡 แนวทางการตอบที่ถูกต้องตามหลักวิศวกรรม:

"Google Sheets เหมาะสำหรับงานต้นแบบ (Proof-of-Concept) แต่หากขยายเป็น 100 โหนดจะเริ่มติดข้อจำกัดเรื่อง Concurrent Write Limit (ไม่เกิน 30-50 ครั้งต่อนาที) และความช้าของ HTTP Protocol ครับ หากต้องสเกลทั้งวิทยาเขต ควรยกระดับสถาปัตยกรรมเป็น 3 ระดับ:

1. เปลี่ยนโปรโตคอลเป็น MQTT: ส่งข้อมูลผ่าน MQTT Broker แบบ Publish/Subscribe ซึ่งใช้แบนด์วิดท์น้อยกว่า HTTP ถึง 90% และประหยัดพลังงานบอร์ดอย่างมาก
2. เครือข่ายส่งข้อมูลระยะไกล LoRaWAN / NB-IoT: พื้นที่ทางเดินกว้างที่ไม่มี Wi-Fi สามารถใช้คลื่น LoRa ยิงสัญญาณเข้า Gateway กลางได้ไกล 5-10 กิโลเมตร
3. ระบบฐานข้อมูล Time-Series DB: เปลี่ยนไปใช้ฐานข้อมูลเฉพาะทาง เช่น InfluxDB หรือ PostgreSQL ร่วมกับแดชบอร์ดระดับอุตสาหกรรมอย่าง Grafana ซึ่งสามารถรองรับข้อมูลระดับหมื่นทรานแซกชันต่อวินาทีได้อย่างมีเสถียรภาพครับ"

⚠️ ข้อควรระวัง / สิ่งที่ห้ามตอบเด็ดขาด: ห้ามตอบว่า "Google Sheets ใช้ได้ไม่จำกัด เพิ่มเป็นล้านโหนดก็ไหว" เพราะแสดงถึงความไม่เข้าใจข้อจำกัดของซอฟต์แวร์

}
